# Codex 与 Claude Code 使用指南：从入门到高效协作

Codex 和 Claude Code 都不只是“帮你补全代码”的聊天机器人。它们可以读取项目、搜索代码、修改文件、运行命令、执行测试，并根据结果继续修正。真正决定效果的，通常不是你用了哪个模型，而是你是否提供了清晰目标、项目约束和可执行的验收方式。

本文介绍两款工具的基础用法、核心配置、高效工作流与安全技巧。文中命令与功能依据官方文档整理，资料核对日期为 2026 年 8 月 4 日。

## 一、先理解它们的工作方式

一次典型的智能编码任务可以拆成下面几个阶段：

1. 理解目标和限制。
2. 检查仓库结构与现有实现。
3. 制定修改方案。
4. 编辑文件并运行命令。
5. 执行测试、构建或页面检查。
6. 根据验证结果继续修复。
7. 汇总修改内容和剩余风险。

因此，高质量请求不应该只有“帮我优化一下”，而应尽量包含目标、范围、限制和验收标准。

例如：

```text
请修复登录页面刷新后丢失用户状态的问题。

范围：只修改 src/auth 和相关测试。
限制：不要改变现有 API；不要引入新依赖。
验收：刷新页面后仍保持登录状态，退出登录逻辑不受影响。
验证：运行 auth 单元测试和项目构建，并报告结果。
```

## 二、Codex 快速入门

### 1. 安装和启动

macOS 或 Linux 可以使用官方安装脚本：

```bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
```

进入项目目录并启动：

```bash
cd your-project
codex
```

首次启动时按照提示登录。建议始终在具体项目目录中启动，这样 Codex 能正确识别 Git 根目录、项目指令和可操作范围。

### 2. 常用交互命令

```text
/init         创建项目级 AGENTS.md 指令文件
/status       查看模型、目录和权限等当前状态
/permissions  调整允许 Codex 执行的操作
/model        选择模型和推理强度
/review       审查当前代码改动
```

普通对话适合探索和持续修改；一次性任务或自动化脚本可以使用非交互模式：

```bash
codex exec "运行测试，分析失败原因，但不要修改代码"
```

### 3. 使用 AGENTS.md 固化项目规则

`AGENTS.md` 用来告诉 Codex 项目中长期有效的信息，例如：

- 项目架构和目录职责。
- 安装、测试、构建命令。
- 代码风格和命名规范。
- 禁止修改的文件。
- 完成任务前必须执行的检查。

示例：

```markdown
# 项目说明

- 这是一个 Jekyll 静态博客。
- 文章放在 `_posts/<category>/` 中。
- 新文章文件名必须使用 `YYYY-MM-DD-slug.md`。

# 验证命令

- 修改文章后运行 `python3 update_posts_data.py`。
- 提交前运行 `docker compose up --build -d`。
- 验证 `/post.html` 和新增文章 URL 返回 HTTP 200。

# 安全限制

- 不要提交 `.env`、密钥或本地凭证。
- 不要使用破坏性 Git 命令覆盖用户修改。
```

Codex 会从项目根目录向当前工作目录逐层读取 `AGENTS.md`。更靠近当前目录的指令可以覆盖上层规则，因此大型仓库可以给不同模块设置不同要求。

### 4. 权限和沙箱

Codex 将“是否需要询问”和“命令能访问什么”分开控制：

- `approval_policy` 决定什么时候暂停并请求批准。
- `sandbox_mode` 决定文件系统和网络访问范围。
- `read-only` 适合代码阅读和审查。
- `workspace-write` 适合日常开发，只允许修改工作区。
- `danger-full-access` 风险最高，只应在隔离环境中谨慎使用。

个人配置通常位于 `~/.codex/config.toml`，项目配置可以放在 `.codex/config.toml`。不要为了少点几次确认，就直接开放全磁盘和无限制网络访问。

## 三、Claude Code 快速入门

### 1. 安装和启动

macOS、Linux 或 WSL 推荐使用原生安装方式：

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

确认安装状态：

```bash
claude --version
claude doctor
```

进入项目并启动：

```bash
cd your-project
claude
```

### 2. 常用 CLI 命令

```bash
# 带着初始任务进入交互会话
claude "解释这个项目的架构"

# 执行一次任务并退出，适合脚本
claude -p "运行测试并总结失败原因"

# 继续当前目录最近一次会话
claude -c

# 将日志通过管道交给 Claude 分析
tail -200 app.log | claude -p "找出异常并给出排查顺序"
```

会话中常用命令：

```text
/init                 生成 CLAUDE.md
/context              查看上下文使用情况
/clear                清空当前上下文，开始无关的新任务
/compact <instructions>  按指定重点压缩会话上下文
```

### 3. 使用 CLAUDE.md 固化项目规则

Claude Code 会在会话开始时读取 `CLAUDE.md`。适合记录构建命令、编码规范、架构约束和工作流程。

```markdown
# Commands

- Install: `npm ci`
- Test: `npm test`
- Typecheck: `npm run typecheck`
- Build: `npm run build`

# Code style

- 使用 TypeScript strict 模式。
- 优先复用现有组件，不重复实现工具函数。
- 修复 Bug 时必须添加回归测试。

# Workflow

- 修改前先阅读相关模块和测试。
- 完成后运行最小相关测试，再运行构建。
- 不要修改生成文件和第三方依赖目录。
```

常见作用域包括：

- `~/.claude/CLAUDE.md`：个人所有项目通用规则。
- 项目根目录 `CLAUDE.md`：团队共享规则，适合提交到 Git。
- `CLAUDE.local.md`：个人项目规则，通常加入 `.gitignore`。
- 子目录中的 `CLAUDE.md`：针对具体模块的局部规则。

文件应该短而明确。仅在特定任务中偶尔使用的流程，更适合做成 Skill，而不是全部塞进 `CLAUDE.md`。

### 4. 权限模式

Claude Code 提供多种权限模式，可以在 CLI 中按 `Shift+Tab` 切换常用模式：

| 模式 | 适用场景 |
|---|---|
| `default` / Manual | 新项目、敏感项目，需要逐步确认 |
| `acceptEdits` | 允许自动编辑文件，适合日常迭代 |
| `plan` | 只分析和规划，避免过早修改代码 |
| `auto` | 长任务，由安全检查控制自动执行 |
| `dontAsk` | 只运行预先允许的工具，适合受控脚本 |
| `bypassPermissions` | 跳过权限检查，仅限隔离容器或虚拟机 |

启动时进入计划模式：

```bash
claude --permission-mode plan
```

不要在包含生产密钥、个人文件或重要未提交修改的环境中使用 `bypassPermissions`。

## 四、通用高效提示词模板

一个稳定的任务描述可以包含六部分：

```text
目标：要实现什么结果？
背景：为什么要改，当前行为是什么？
范围：允许检查和修改哪些目录？
限制：哪些接口、依赖或行为不能改变？
验收：什么结果代表任务完成？
验证：需要运行哪些测试、构建或页面检查？
```

### Bug 修复模板

```text
现象：上传大文件时进度条停在 99%。
期望：上传成功后显示 100%，然后进入完成状态。
范围：检查上传状态管理和相关组件。
限制：不要修改服务端 API。
要求：先复现并解释根因，再实施最小修复；添加回归测试并运行。
```

### 重构模板

```text
重构 src/services/payment.ts，拆分支付渠道适配逻辑。
保持所有公开函数签名和业务行为不变。
先列出调用方和风险，再给出计划；经现有测试验证后再总结改动。
不要顺手修改无关格式或命名。
```

### 代码审查模板

```text
审查当前分支相对 main 的差异。
重点检查正确性、并发问题、安全风险和缺失测试。
只报告可以具体行动的问题，按严重程度排序，并标出文件与行号。
不要修改代码。
```

## 五、最有效的工作流：探索、计划、实现、验证

### 1. 探索

先让工具回答：

- 功能入口在哪里？
- 数据如何流动？
- 哪些测试覆盖了它？
- 当前分支是否有未提交修改？
- 哪些文件是生成文件或禁止编辑？

示例：

```text
先阅读登录流程、路由守卫和相关测试，画出状态流转。
这一阶段只分析，不修改文件。
```

### 2. 计划

要求计划包含：

- 修改文件列表。
- 每个文件为什么要改。
- 兼容性和回滚风险。
- 验证命令。

任务越大，越应该把探索与实现拆开，避免工具快速写出“看似正确但解决错问题”的代码。

### 3. 实现

实现阶段坚持小范围修改：

- 一次只解决一个明确问题。
- 复用现有模式和依赖。
- 不进行无关重构。
- 定期检查 `git diff`。
- 发现方向错误时尽早纠正，不要等任务结束。

### 4. 验证

给智能编码工具一个它能自行判断的完成信号：

- 单元测试或集成测试。
- 编译、类型检查和 lint。
- HTTP 状态码或 API 响应。
- 浏览器截图与设计稿对比。
- 生成文件与基准文件的差异。

不要只要求“确认可以运行”，而要要求它执行命令并展示证据：

```text
完成后运行相关测试和生产构建。报告执行的命令、退出状态、失败项和未验证部分。
```

## 六、上下文管理技巧

### 1. 一个会话只处理一个主题

不要在修复登录问题的长会话中，突然要求设计数据库、翻译文档和重写首页。无关内容会挤占上下文，降低后续判断质量。

### 2. 及时开启新会话

适合开启新会话的情况：

- 上一个任务已经完成。
- 工作目标发生明显变化。
- 会话中积累了大量无关日志。
- 工具反复忘记约束或偏离方向。

Claude Code 可以使用 `/clear` 清空上下文，也可以用 `/compact` 保留指定重点。Codex 中可以开启新任务，并把稳定规则放进 `AGENTS.md`，避免依赖聊天历史。

### 3. 不要一次贴入整个仓库

告诉工具文件路径、错误信息和复现方式，让它按需读取。对于日志，先提供错误附近的内容，再根据分析补充上下文。

## 七、Git 与安全技巧

### 1. 开始前建立检查点

```bash
git status
git diff
```

重要任务可以先提交当前工作，或者创建新分支：

```bash
git switch -c feature/ai-assisted-change
```

### 2. 明确保护用户修改

在请求中注明：

```text
保留工作区中已有的未提交修改，不要覆盖、重置或删除无关文件。
```

### 3. 密钥不进入上下文和仓库

- 不要粘贴真实 API Key、Cookie、私钥和生产密码。
- 将 `.env` 加入 `.gitignore`。
- 日志中包含凭证时先脱敏。
- 不允许工具读取与任务无关的个人目录。

### 4. 高风险命令必须人工确认

以下操作需要特别谨慎：

- 删除文件或数据库数据。
- `git reset --hard`、强制推送。
- 修改生产环境。
- 大范围依赖升级。
- 跳过权限检查。

## 八、Skills、MCP 与 Hooks 应该何时使用

### Skills

适合封装可重复的任务流程，例如：

- 创建符合团队规范的 API。
- 发布博客文章。
- 执行 PR 审查。
- 构建并验证 Docker 镜像。

### MCP

适合连接外部工具和数据，例如 GitHub、数据库、监控平台、设计文档和工单系统。只连接可信服务器，并为写操作保留审批。

### Hooks

适合执行确定性的自动检查，例如：

- 编辑文件后运行格式化。
- 提交前执行 lint。
- 阻止修改受保护路径。
- 任务结束前检查测试是否通过。

静态项目规则应放在 `AGENTS.md` 或 `CLAUDE.md`；可复用流程放进 Skill；外部数据连接使用 MCP；必须机械执行的检查使用 Hook。

## 九、Codex 与 Claude Code 如何选择

| 需求 | 建议 |
|---|---|
| 终端内阅读、修改、测试代码 | 两者都适合 |
| 希望使用 OpenAI/Codex 桌面、云任务和插件生态 | 优先考虑 Codex |
| 已深度使用 Claude、CLAUDE.md、Hooks 或 Agent Teams | 优先考虑 Claude Code |
| 需要脚本化一次性任务 | `codex exec` 或 `claude -p` |
| 敏感仓库分析 | 使用只读或计划模式 |
| 大型任务 | 先计划，拆成多个可验证的小任务 |

最实用的方法不是争论哪一个绝对更强，而是用同一类真实任务进行比较：完成时间、修改范围、测试通过率、人工返工量和上下文成本。

## 十、常见失败方式

### 1. 请求过于宽泛

错误：

```text
帮我优化项目。
```

改进：明确性能目标、页面范围、兼容要求和验收指标。

### 2. 没有验证标准

只说“写完即可”会让工具把代码存在视为完成。应明确测试、构建、截图或可观察行为。

### 3. 让工具一开始就大改

复杂任务先分析再计划。尤其是认证、支付、数据库迁移和部署配置，不要在不了解现状时直接重写。

### 4. 指令文件太长

`AGENTS.md` 和 `CLAUDE.md` 应记录稳定且重要的规则。过多背景资料会稀释真正关键的限制。

### 5. 盲目开启最高权限

减少确认弹窗不等于提高效率。更好的做法是允许明确、安全且重复的命令，并对删除、生产写入和敏感目录保持审批。

## 总结

高效使用 Codex 和 Claude Code，可以记住五条原则：

1. 给出清晰目标、范围、限制和验收标准。
2. 复杂任务遵循“探索 → 计划 → 实现 → 验证”。
3. 用 `AGENTS.md` 或 `CLAUDE.md` 保存稳定项目规则。
4. 给工具可执行的测试或构建命令，让它自行闭环。
5. 使用最小必要权限，并通过 Git 保留可恢复的检查点。

当智能编码工具能够理解项目规则、看到明确目标，并独立执行验证时，它才真正从“代码生成器”变成可靠的工程协作者。
